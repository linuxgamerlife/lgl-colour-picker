## GTK Migration Session — 2026-10-18

The project is migrating from Qt 6 to a GTK 4/gtkmm application following
`/development/projects/docs/gtk-desktop-application-standard.md`, using
`/development/projects/lgl-papercutter` as the structural reference.

### Current GTK Foundation

- The repository root `CMakeLists.txt` now builds `gtk/` only. Legacy Qt files
  in `src/` and `resources.qrc` are retained as implementation reference and
  are not built.
- `gtk/CMakeLists.txt` requires gtkmm 4.20+, libadwaita 1.6+, CMake 3.20+,
  C++20, strict warnings, and provides
  `LGL_COLOUR_PICKER_ENABLE_SANITIZERS`.
- GTK application code is under `gtk/src/`, with pure/tested colour, settings,
  and theme helpers under `gtk/src/core/`; UI code is under `gtk/src/ui/`.
- `ThemeWatcher` follows the Papercutter implementation: it tracks libadwaita
  dark/accent changes, GNOME interface settings, and GTK user CSS (including
  local imports), then reapplies colours, mono font, and the window dark class
  after a 200 ms debounce. This keeps the picker aligned when the system theme
  changes while it is running.
- `style.css`, `HELP.md`, and the 256px icon are bundled in the GResource
  prefix `/com/linuxgamerlife/colourpicker/`.
- The app ID is now `com.linuxgamerlife.lgl-colour-picker`. New desktop and
  metainfo files use that ID; the metainfo declares the old
  `io.github.linuxgamerlife.lgl-colour-picker` identity as a provided ID.
- The GTK shell currently provides branding, initial colour-format rows,
  clipboard copy, application CSS, and basic core tests. `Pick Colour` now
  starts an asynchronous XDG Desktop Portal `PickColor` request and updates
  the current colour from a valid portal response. The current colour preview
  is a `Gtk::DrawingArea`, redrawn when that colour changes. This is available
  in the development binary `build-gtk/lgl-colour-picker`; an existing
  installed 1.0.1 RPM and the prior `build/` binary are still the Qt
  application.
- The header and main menu now follow the Papercutter order: the primary Pick
  Colour action appears beside the rightmost main-menu button, and menu
  sections contain Pick Colour, Use System Title Bar, Help, About, and Quit.
  `Ctrl+Shift+M` persists and switches the title-bar mode, and `F1` opens the
  bundled `HELP.md`; the About dialog follows the shared LGL fields.

### Environment-Agnostic Picking Policy

- Do not add Niri, Noctalia, `grim`, `slurp`, `wl-copy`, or compositor checks
  to the GTK implementation or runtime dependencies.
- Wayland picking will use the XDG Desktop Portal `PickColor` API
  asynchronously. When no compatible portal backend is available, show a clear
  user-facing failure notice.
- The portal picker surface belongs to the selected desktop portal backend, not
  to the GTK application. The app must not attempt to impose its CSS or theme
  on that surface. During this session, KineticWE selected its `kwe` portal
  backend for `org.freedesktop.portal.Screenshot`; any unreadable light portal
  picker is therefore a KineticWE portal-theme issue.
- X11 will have an isolated native overlay/pixel-sampling adapter. It must not
  be loaded or used under Wayland.
- The portal request must be cancellable and closed on window/controller
  teardown. Helper-process fallbacks from the Qt build are intentionally not
  being ported.

### Packaging Decision

- `qt6-qtwayland`, `grim`, and `slurp` are no longer dependencies or RPM
  recommendations. The GTK RPM spec explicitly requires only
  `xdg-desktop-portal`; GTK and libadwaita shared-library dependencies are
  generated by RPM.
- The spec build requirements now name gtkmm, libadwaita, GLib, Ninja, and
  modern CMake. It still needs the standard source archive/Makefile conversion
  before release.

## Wayland Behaviour

Wayland cannot be handled by arbitrary screen pixel reads in a compositor-neutral
way. The app uses this order:

1. XDG Desktop Portal `org.freedesktop.portal.Screenshot.PickColor`.
2. Niri fallback through `niri msg pick-color` when running under Niri.
3. `grim`/`slurp` fallback where supported.
4. Qt screen-grab overlay only outside Wayland.

`grim`/`slurp` are not universal Wayland APIs and may not work on compositors
such as Niri. The portal path is the preferred cross-compositor route.

## Runtime Dependencies

RPM auto-generates linked Qt library requirements, but the spec explicitly
requires:

- `qt6-qtwayland`
- `xdg-desktop-portal`

The spec recommends:

- `grim`
- `slurp`
- `wl-clipboard`

A portal backend is also required for portal colour picking. Fedora Workstation
and Fedora KDE usually provide one. Minimal Fedora or custom compositor setups
may need portal/backend configuration.
